## What I did check

- Every file parses as JSON, has the required top-level and nested fields, and is **under 5,000 bytes** (stricter than 5 KiB).
- All part kinds and materials are from the whitelists; required IDs, tags, roles and item names are shaped correctly.
- Every dependency points to an existing part. There are no duplicate IDs, self-dependencies or support cycles.
- Simulated the documented axis-aligned rotated-box rules for plot bounds, height, ground standing, support contact (0.04 tolerance), overlap (0.02 tolerance), wire and direct-support exceptions.
- Checked system references, inventory capacities, worker roles, deliveries, production, power ranges, sales, repair and effect tags against the documented rules.
- Ran the above in **an independent local Python checker mirroring the published rules**. All ten passed that local checker. Verified ZIP contains the required twelve files.

## What I did NOT check

- **Did not run the project's original `validate.js`** against these files; the source was inspected via public web view, but not downloaded into the execution environment. Original-validator confirmation is **pending**.
- **Did not run** `build.js`, `sim.js`, robot tests, an actual three.js scene, or real iPad/AR tests. No visual quality, animation, collision behaviour under full physics or economic balance has been proven.
- Did not ask any local models or third-party AIs, use the user's home machines, push to GitHub, install anything or launch game jobs.

## Fields and behaviours with uncertainty

1. `repair.worker_roles: []` on the cottage is structurally permitted by the published schema, but gives it no worker able to repair parts. Treat as a gameplay limitation.
2. `power.supply_kw` is **external power received**, not generated by a windmill or power shed. A power shed is currently a maintenance/consumption building, not a generator.
3. Static `beam` used for windmill sail; neither true rotation nor wind-driven output is in the schema.
4. Building names do not give homes residents, schools learning, lighthouses a beacon, boats buoyancy or barns growing crops. Those systems are absent.
5. The roof strips use valid supports and small gaps by the published geometry; actual rendered appearance and mechanical plausibility still need inspection.
6. The money and throughput figures are illustrative; the validator only checks ranges, not economy fairness.

## Recommended verification on a computer with the game branch

1. Feed each `recipes/recipe_XX.json` into the real `CityValidate.parse(text)` and record any returned errors; do **not** silently patch the JSON.
2. Load passing recipes into City Lab one at a time; check for roof gaps, object orientation, fake machinery and floating-looking items.
3. Run the project's test suites, then an on-device iPad performance test with just one building before trying four.
4. Reject a recipe if the player cannot understand which parts matter; only then consider adding missing part kinds.
